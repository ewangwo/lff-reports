1

Token → Embedding：模型如何理解文字

大模型不是"认识"文字。它只认识一种东西：一串数字（向量）。从文字到向量的转化，是整个链条的第一步。

完整链路

文本 → 按词表切分 → Token ID → Embedding 查表 → 向量 [0.12, -0.35, ...] → Transformer 计算

关键理解

  • Token ID ≠ 语义——"猫→1024"、"狗→1025"编号接近不意味着含义接近，编号只是"图书馆索书号"
  • Embedding 不是人手动标注的——模型从大量文本统计出：同时出现的词在向量空间中靠近
  • 语义地图——猫/狗/兔子在一个区域，汽车/发动机/轮胎在另一个区域
  • 同一个词在不同上下文向量不同——"苹果"在"苹果很甜"和"苹果发新机"中最终向量不同
💡 对程序员的理解： Embedding 层本质上是一张查表（Lookup Table）——行数 = 词表大小（~100K），列数 = 隐藏维度（~4096）。模型拿 Token ID 直接索引对应行，不需要矩阵乘法。
2

推理为什么"先慢后快"：Prefill × Decode

LLM 推理不是一次前向就完事——它分成两个阶段，瓶颈完全不同。

Prefill（预填充）Decode（解码）
做什么一次性处理全部输入 token逐 token 生成，自回归循环
瓶颈计算密集型（吃算力）内存带宽密集型（吃带宽）
关键指标TTFT（Time To First Token）ITL（Inter-Token Latency）
慢在哪长 prompt 时，等"第一句话"输出像"挤牙膏"，一句一句来
优化方向减少 prompt 长度、Prefix CacheKV Cache 优化、推测解码
🔑 一句话诊断：
长 prompt 慢 → 优化 TTFT（Prefill 问题）
输出挤牙膏 → 优化 ITL（Decode 问题）
同一个请求的两个阶段，优化方向完全不同。

为什么 Decode 是内存瓶颈？

每生成一个 token，都要从显存读取全部 KV Cache 到计算单元。一个 70B 模型在 8K 上下文下，KV Cache 可以占满 80GB 显存。每次读取 80GB 数据所花的时间，远大于计算这 80GB 所花的时间。

GPU 计算单元大部分时间在"等数据"——这就是"内存墙"（Memory Wall）。

3

KV Cache：空间换时间的核心瓶颈

KV Cache 的核心作用是缓存历史 token 的注意力计算结果，避免每一步都重新计算全部上下文。但这把双刃剑——省了计算，吃了显存。

为什么 KV Cache 这么大？

KV Cache 大小 = 层数 × 隐藏维度 × 上下文长度 × 批处理大小 × 2（K+V）
13B 模型：~1MB/token → 4K 上下文 ≈ 4GB

KV Cache 的放大效应

KV Cache 越大 → 单卡能同时服务的请求越少 → 摊到每个请求上的 GPU 成本越高。所以：KV Cache 压缩 10 倍 = 每请求成本降 10 倍。

常见的 KV Cache 优化

  • 量化：FP16→INT8→INT4，精度换空间（FP32 28GB → FP16 14GB → INT8 7GB → INT4 3.5GB）
  • Sliding Window：只保留最近的 N 个 token
  • Prefix Cache：跨请求复用相同的上下文前缀
  • PagedAttention：分页化管理 KV Cache，消除碎片
  • MLA（终极方案）：见第5章
⚠️ 核心矛盾： KV Cache 减少计算量，但把系统压力从算力转移到内存。优化计算之后，问题并没有消失，而是被"转移"了。
4

注意力机制进化史：MHA → GQA → MLA → CSA

标准的多头注意力（MHA）是"重"的——每个注意力头都有独立的 K、V 投影。进化方向只有一个：减少 KV 数量，压缩缓存。

机制核心思想K/V 头数KV Cache 节省代表模型
MHA 每个注意力头有独立 K、V Q 头数 = K 头数 = V 头数（如 32） 1x（基线） GPT-3, LLaMA 1
MQA 所有 Q 共享一组 K、V K=V=1 头 ~32x PaLM, Falcon
GQA Q 分组共享 K、V K=V=组数（如 8） ~4x LLaMA 2/3, Mistral
MLA K、V 压缩到低维潜在空间 存 c（d_c≈d/5），临时展开 ~5x DeepSeek V2/V3
CSA+HCA 交叉注意力共享 KV + 混合压缩 交叉注意力层共享 ~5x+ DeepSeek-v4
📐 MLA 的原理：
标准 MHA：x → K 和 V（两个独立的投影矩阵，存 2d 个元素/token）
MLA：
  第一步：x → c（降维到 d_c ≈ d/5）
  第二步：需要时 c → K, c → V（升维展开）
  只存 c，不存 K、V。
省内存 5x，省带宽 5x，需要额外计算但远小于省下的带宽。

DeepSeek 三件套：MLA × MoE × MTP = 20x

MLA × MoE × MTP ≈ 20× 成本差
不是补贴烧钱，是架构代差——API 价格差距的技术解释
维度Baseline 70B DenseDeepSeek V3优化倍率
KV Cache 显存 每 token 每层 2d 元素 MLA：d_c ≈ d/5 ~5x
激活参数 70B 全激活 MoE：37B/671B ~2x（vs 70B Dense）
Decode 效率 1 token/前向 MTP：2 token/前向 ~2x
综合（乘法关系） ~20x

① MLA — 省显存

  • K 和 V 不是独立的信息源，共享底层表示
  • 降维到潜在空间（d≈7168 → d_c≈512），存 c 不存 K/V
  • 效果：同样 GPU 可服务 5-10 倍并发请求
  • 隐形收益：支持更长上下文
  • 代价：需要专用 CUDA kernel，不能直接用 FlashAttention

② MoE — 省计算

  • 总参 671B，256 个路由专家 + 共享专家
  • Router 每 token 选 Top-8 激活，每次前向只算 37B 参数
  • 效果：671B 模型，计算量只相当于 37B
  • 难点：负载均衡（"专家坍塌"）、跨节点通信
🤝 MLA + MoE 互补：
MLA 压 KV Cache（显存瓶颈），MoE 压 FFN 计算（算力瓶颈）。两者各管各的瓶颈，互不干扰。

③ MTP — 提吞吐

  • 标准 Decode：一次前向 1 个 token → MTP：一次前向 2 个 token
  • 在主输出层之上加额外预测头，N=2 性价比最优
  • 效果：吞吐量翻倍，可充当投机解码草稿模型
  • 成本：训练时微增，推理时几乎零额外成本

为什么 OpenAI / Google 不直接抄？

  • MoE 工程复杂度：671B MoE 训练需要处理负载均衡、节点路由、不稳定性
  • 推理部署路径依赖：大厂用超大规模集中推理 + 定制硬件（TPU）摊薄成本
  • MLA 兼容性成本：标准 MHA 有成熟 FlashAttention，MLA 需重写 CUDA kernel
  • 核心策略差异：DeepSeek 用算法创新弥补硬件的限（H800），大厂用最强硬件换时间

DeepSeek V3 推理过程全景

Prefill：
Tokenize 输入 → MLA：存压缩 c 到 KV Cache → MoE Router：选 8/256 专家
Decode（逐 token）：
MTP：一次预测 2 token → Q 标准投影 → K/V 从 c 展开 → MoE 选专家子集 → 新 token 的 c 追加到 KV Cache
MLA 控制显存 · MoE 控制计算量 · MTP 控制吞吐密度

推理瓶颈从算力转向带宽：谁搬得少谁赢

🏆 全文核心命题： 推理性能的竞争，正在从"谁算得更快"转向"谁搬得更少"。

传统认知：大模型慢 → 参数太多 → 算力不够。这套解释正在失效。

实际瓶颈是：自回归推理 → 每步加载完整权重 → 数据搬运 >> 计算本身。

优化方向在收敛：

  • 量化 → 降权重精度，减内存占用
  • KV Cache 复用 → 避免重复加载历史
  • 推测解码 → 用小模型预测，减大模型调用
  • Prefix Cache → 跨请求复用上下文
  • MLA → 压缩 K/V 到潜在空间
共通点： 不再追求"更快算"，而是尽量少搬数据、少访问权重。当带宽成为主约束，优化目标就从提升算力利用率转向降低数据访问成本。
